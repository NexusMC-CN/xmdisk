# 02 · 存储层设计

## 总体：元数据面与数据面分离

- 元数据面：SQLite（WAL 模式，modernc.org/sqlite 纯 Go 构建）。条目表、buckets、creds、oplog、slaves 同库——**同事务原子性**是配额计数、oplog 一致性、崩溃安全的共同根基。
- 数据面：内容寻址 blob 仓库（SHA-256）。容量走数据面，元数据库大小只随对象数增长，与字节数无关。
- 事件日志只走元数据和 blob 引用（哈希），**永不走文件内容**——同步的"准确性"（日志保证顺序）与"耗时"（blob 慢慢拉）互不干扰。

## 数据面

- 小文件（< 4MB，可配）整文件一个 blob；大文件 8MB 定长分块（内容定义分块 CDC 留作将来）。
- blob 按 sha256 存储，两级前缀分目录：`blobs/ab/cd/<full-hash>`（256×256，防单目录百万文件）。
- 入库单遍流式：TeeReader 边落盘边算哈希，不读两遍；blob 写入完全并行；ack 前 fsync 数据文件，再提交元数据事务（存储产品宁可慢不可撒谎）。
- **符号链接加固（99-D018）**：blob 一切路径操作 Lstat 强制普通文件，分片目录链必须真实目录，trash 链接只删不复活，Put 铲除链接占位重写——防存储目录内被植入指向外部的跳板链接。
- **流式配额守卫（99-D019）**：写 blob 前预读桶计数快照设写入上限，超额即刻中断、磁盘零残留；权威校验仍在事务内。
- 对象内容 = 有序 blob 引用列表。S3 multipart 的每个 part 就是一个 blob，CompleteMultipartUpload 只写元数据不物理拼接；Ranged GET 跨 blob 做偏移计算。
- 去重：同内容 blob 天然共享。**不用引用计数**（崩溃/并发下会丢数据），用标记-清扫 GC。

## 元数据模型

entries 表核心字段（完整定义见 04）：

- `bucket, key`：key 按原始字节保序存储（S3 List 依赖字典序，注意二进制 key 编码）；
- `type`：file / dir——树形协议（SFTP/WebDAV）需要显式目录条目（空目录、目录 mtime/权限）；S3 PUT `foo/` 约定产生 dir 条目；
- `size`（逻辑字节）、`etag`（对外：单发 PUT=MD5，multipart=协议合成值；与内部 sha256 严格分离）；
- `blobs`：有序引用 `[{sha256, size}]`；
- `content_type`、`user_meta`（WebDAV 死属性也存这里）、posix 属性（uid/gid/mode，S3 写入给默认值）、`mtime`、`seq`。

multipart 进行中会话：本地表，不复制（见 99-D010）。

## 复制模型（概要，详见 03）

- oplog：**全量状态 op**（非增量 diff）、幂等、seq 单调有序、带 epoch。JSON 编码（可用 sqlite3 肉眼排障）。
- 从节点循环：批量拉 op → 并行补齐 blob（限速、指数退避、墓碑感知）→ 本地事务按序回放。blob 未到位不回放该 op。
- 新从节点 / 落后超限者：快照（VACUUM INTO，含截断点 seq）+ 追赶。
- 日志截断：保留到 min(所有已注册从节点 ack seq, 最新快照 seq) − 宽限期；无从节点 ack 则不截断。

## 删除与 GC

- 条目层：DELETE op 即墓碑，从节点重放即记录删除状态，物理清除由后台任务处理。
- blob 层两阶段 GC：
  1. **标记**：定期扫描存活条目，无引用 blob 移入"待删除"（带时间戳），不物理删；
  2. **清扫**：超过宽限期（默认 48h 可配）且所有已注册从节点 ack 已越过使其失效的 op，才物理删除。**清扫前必须重新验证存活，不信标记本身**（自愈：崩溃/并发/bug 最坏是多留空间，不会误删）。
- 从节点 GET 到墓碑 blob：主节点返回明确的墓碑状态（非 404），从节点记录"已知已删"并跳过——消除"删除与同步赛跑"的重试风暴。
- admin 提供"立即清扫"；multipart 超时（默认 7 天 abort）同样走 GC 路径。

## 配额与用量

- buckets 表维护 `used_bytes / pending_bytes / object_count`，与条目变更、oplog 追加**同一事务**更新：零漂移（无崩溃中间态）、无竞态（SQLite 写串行，check-and-increment 天然原子）。
- 口径：**计费与配额都用逻辑字节**（客户视角对象大小，与 S3 计费一致）；物理字节（去重后落盘）仅作指标，差值 = 去重收益。
- multipart parts 落盘即计入 `pending_bytes`，Abort/超时退还——堵住"配额内无限传 part"的洞。
- 日快照表（桶/天一行 used_bytes/object_count）供计费对账取证；实时值走 admin 查询与 Prometheus gauge。
- 每日离峰 `SUM(logical_size)` 重算比对计数器，不一致以重算为准修正并告警（对抗 bug 的保险，理论上永不触发）。
- 流量按桶导出指标（计费归网关，数字顺手就有）。

## 凭据与主密钥

- creds 表：`access_key`（明文，非机密）、加密 secret、绑定桶（一凭据一桶起步）、启停位。S3/SFTP/WebDAV 三协议共用。
- SigV4 验签要求持有明文 secret 重算 HMAC，**不能单向哈希** → secret 以 AES-GCM 加密落库，主密钥（KEK）来自环境变量（开发期 .env）。
- KEK 是**部署级共享**：所有节点同值（从节点提升后必须能验签；oplog 复制的是密文）。
- KEK 丢失恢复流程：新 KEK 启动 → health 自检报"N 条 secret 不可读" → admin 批量重置（业务平台提交其留存的明文，或 `rotate` 由我方生成新 SK 一次性返回，平台可不留副本）。SigV4 每请求无状态验签，重置即刻生效。
- **红线：KEK 只保护可重置状态。** 若将来做 blob 静态加密，其密钥丢失 = 数据永久丢失，必须进备份流程，与 KEK 严格分离、永不混用。
