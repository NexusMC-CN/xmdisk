# 03 · 复制与灾备

## 角色模型

- role（master / slave）是**部署配置，不是节点身份**。从节点只同步，不对外服务。
- 不做多主、不做自动切换。自动化原则：**机器只做校验和执行，决策永远由运维做出**——每个 admin 动作命令自带前置校验（不满足即拒绝并说明原因），每一步都有对应的验证命令。拒绝黑盒。
- epoch（uint32）：oplog 与 ack 都携带。promote 时 epoch+1；任何节点拒收低 epoch 数据。用于防"旧主复活后双写"。

## 节点状态机

| 开关 | 取值 | 说明 |
|---|---|---|
| role | master / slave | 初始由配置声明；运行期只能通过 promote 改变 |
| serve（数据面） | off / ro / rw | slave 恒为 off；promote 后默认 ro；rw 需显式开启 |
| sync（同步循环） | stopped / running | 从节点的拉取循环，各节点独立控制 |

关键不变量：**写入只发生在 role=master 且 serve=rw 的节点**；任何时刻至多一个这样的节点（由运维的流程保证，epoch 兜底）。

## 复制协议（repl 端口）

| 接口 | 说明 |
|---|---|
| `GET /repl/oplog?after=&limit=` | 批量拉 op |
| `GET /repl/snapshot` | 元数据快照文件（VACUUM INTO，含截断点 seq） |
| `GET /repl/blob/{sha256}` | 墓碑感知：返回内容 / 墓碑状态 / 不存在 |
| `POST /repl/register` | 从节点登记，进入日志截断与 GC 门控计算 |
| `POST /repl/ack` | 汇报 {slave_id, epoch, last_seq} |

- 主节点 `slaves(id, last_acked, last_seen)` 表 = 日志截断、GC 门控、死从节点判断的共同数据源。
- 截断**永远保留最新一条 op 作 seq 水位线**（seq 分配器=oplog MAX(seq)+1；删光会让 seq 回卷、从节点永久拉不到新 op 且新从被误导入尾拉——集群实测 P1，2026-10-23 修复）。
- 从节点拉取失败一律指数退避 + 预算上限；主节点判定从节点落后超限返回"需重新快照"，从节点转全量流程，不死磕。
- multipart 在途不复制：从节点只拉被 entry 引用的 blob（见 99-D010）。

## 场景 A：主节点离线（灾备提升）

前提：主 M 宕机，从 S1..Sn 运行中，业务当前不可用。

| 步骤 | 操作 | 命令 | 预期 / 验证 |
|---|---|---|---|
| A0 确认与隔离 | 从至少两个网络位置探测 M 的数据 + admin 端口；从反向代理摘除 M；禁止自动拉起（能断电/断网更好） | — | 若 M 实际存活 → 转场景 B 或中止。此步防网络分区误判与复活双写 |
| A1 评估损失、选候选 | 逐台查状态，记录 last_seq 与 epoch | `GET /status` | 候选 = **last_seq 最大（滞后最小）者**。记录候选 seq=N；丢失窗口 = M 上 seq>N 的未同步 op（事后从 M 磁盘 oplog 判断，写入事故报告） |
| A2 停候选同步 | — | `POST /sync {"action":"stop"}` | status 显示 sync=stopped、role=slave（从节点本就不对外服务，无需禁读写） |
| A3 提升候选 | — | `POST /promote` | 命令自带前置校验（role=slave、sync 已停、无半应用 op），不满足即拒绝。预期：role=master、epoch+1、repl 监听开启、serve=ro |
| A4 其余从节点重指 | 每台：sync stop → 改主地址/密钥 → sync start | `POST /sync {"action":"start","master_addr":…}` | 新主 `GET /slaves` 逐台出现且 lag→0（admin 面，2026-10-23 起提供；实操见 docs/08）。**分叉检查**：last_seq ≤ N 直接续传；last_seq > N（比新主更超前）→ 该从分叉，走"旧主处置"的重建流程 |
| A5 流量切换 | 反向代理回源改为新主数据端口 | — | 业务连通性冒烟（GET 一个小对象） |
| A6 恢复读写 | — | `POST /serve {"mode":"rw"}` | 业务侧 PUT/GET 冒烟通过后宣布恢复 |

多从为常态部署。A4 的逐台操作未来可由独立控制台（见 01）批量编排，但必须等价于本表步骤——同一批命令、同样可验证、同样可人工执行。

### 旧主处置（永远人工，不自动）

1. M 修复后**禁止以 master 角色启动**（改配置，且不接入代理）。
2. 需要抢救丢失窗口内的数据时：以 rescue 模式启动（只读、不同步、不进代理），diff 其 oplog 尾部 vs 新主，经 admin 导出接口人工取回指定对象——是否值得抢救是人的决策。
3. 处置完成后加入新主：**保留 blob 目录，清空元数据**，按新从节点流程 bootstrap（快照 + 补缺失 blob）。内容寻址使重建只传缺失部分——16TB 级也只花元数据 + 增量带宽。

## 场景 B：计划迁移（主在线换机）

停机窗口 = B1~B5，分钟级。关键排序：**新机先在业务照常期间完成全量同步，再冻结写入**（16TB 全量 bootstrap 要数天，顺序反了窗口就是数天）。

| 步骤 | 操作 | 命令 | 预期 / 验证 |
|---|---|---|---|
| B0 新机接入 | 部署同版本，配置 role=slave 指向旧主 M1 | `POST /sync {"action":"start",…}` | M1 的 `GET /slaves` 出现 M2，lag 单调降至 0。期间业务照常读写 M1 |
| B1 冻结旧主写入 | M1 切只读 | `POST /serve {"mode":"ro"}` | 业务只读运行；写请求收到明确的 readonly 错误 |
| B2 排空 | 观察 M2（及各从节点）lag | `GET /slaves` | 全部 lag=0。此刻所有节点状态相同，**不存在分叉可能** |
| B3 提升新机 | M2 | `POST /promote` | role=master、epoch+1、serve=ro |
| B4 其余从节点重指 M2 | 同 A4 | — | 无分叉风险（已排空） |
| B5 切流量、恢复 | 代理回源改 M2，开读写 | `POST /serve {"mode":"rw"}` | 业务恢复读写，窗口结束 |

### 旧主 M1 处置（二选一）

- 直接关机留作冷备；或
- 改配置 role=slave 指向 M2，`sync start`，从 seq N 续传——M1 与 M2 同历史，**无需清空重建**。这不是"主转从"专用功能，就是标准从节点接入路径（见 99-D013）。

## 失败处理

- 任一步验证不符：**停在当前状态排查**，不继续后续步骤。
- 场景 A 中 A5 之前业务本就不可用，可从容处理；A5 之后发现问题，优先回退代理再处理节点。
- 场景 B 中 B3 之前可随时 `POST /serve {"mode":"rw"}` 回到原状（迁移中止，代价为零）。
