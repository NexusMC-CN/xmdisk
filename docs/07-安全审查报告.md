# 07 · 安全审查报告（首轮全面检查）

- **审查日期**：2026-10-21
- **审查范围**：全部核心源码（internal/ 13 个包 + cmd/main.go）、Docker/env 配置、docs/01-06 设计文档
- **审查重点**（按用户要求）：
  1. 面向服务使用者的**公共接口**（S3 :9000、SFTP :9001、WebDAV :9000/dav、公共读 :9004）——越权访问、凭据处理、注入、信息泄露；
  2. **存储底层**的可靠性与数据安全（blob/meta/GC/复制/灾备路径）；
  3. admin(:9002)/repl(:9003) 面仅做基本核验（定位为基础设施，额外防护交由使用者：内网/防火墙/反代）。
- **本轮不写代码**，仅检查与立项。本文档兼作**修复进度跟踪表**。

## 总体结论

**未发现可导致越权访问公共接口的高危漏洞（无 P0/P1）**。三协议的桶级凭据隔离（一凭据一桶）、SigV4 验签、内容寻址数据面的路径防护、凭据密封存储等核心机制实现质量高，与文档声明一致。

需要处理的问题集中在三类：

1. **授权面过宽**：数据面（S3）允许持匹配凭据者创建/删除桶，且桶删除后残留凭据可"复活"已删桶（S-01）；
2. **无限增长族**：oplog 无截断任务、GC 清扫可被僵尸 slave 注册永久阻塞、（关联）trash 无限膨胀（S-02/S-03）；
3. **加固项**：弱凭证接受、明文 HTTP 下 WebDAV Basic 传输 SK、公共读面 500 信息泄露等（S-04 起）。

## 二、发现的问题

分级：**P2 = 建议尽快修**（影响授权边界/长期可靠性）；**P3 = 加固与边角**。每条附修复建议与验收口径，修完勾选。

### P2（授权面 / 长期可靠性）

- [x] **S-01 桶删除后残留凭据，可经数据面"复活"已删桶**
  - 位置：`store/store.go:184`（DeleteBucket 不清理 creds）、`s3/handler.go:83`（数据面 PUT 桶 = CreateBucket）
  - 场景：管理员删除空桶 X（绑定 X 的凭据仍存活且 enabled）→ 持旧凭据的客户端对 `PUT /X` 即可重建同名桶，随后正常读写。重建的桶**静默丢失原 quota/public 配置**（quota=nil 不限），管理员以为已下线的命名空间被数据面客户端重新启用。
  - 建议（三选一，倾向①）：
    1. **桶生命周期收归 admin 面**：数据面 S3 的 PUT/DELETE bucket 改 405（凭据只管对象读写，不管桶增删）——与"基础设施、桶由运维供给"的定位一致，同时消掉 S3 DeleteBucket 面；
    2. DeleteBucket 级联删除（或停用）绑定该桶的全部凭据，并出 oplog；
    3. DeleteBucket 前置校验"该桶无凭据绑定"，有则拒绝。
  - 验收：删桶后旧凭据 PUT /X 得 403/405；admin 面可见凭据与桶的绑定关系处置结果。
  - **决议（2026-10-21 第三轮，已定稿）**：桶=租户=一把钥匙，凭据随桶生灭——
    1. **数据面撤桶增删**：S3 `PUT /bucket`、`DELETE /bucket` → 405（保留 HEAD/List/?location 只读；aws mb/rclone mkdir 报错属预期，文档说明）；
    2. **一桶一密**：schema v4 给 creds(bucket) 建唯一索引；建桶即同事务发钥（bucket_create + cred_put 双 op），`POST /buckets {name, quota?, public?, access_key?}` 一次返回 AK+SK（SK 服务端生成仅回一次；access_key 可选，不传则生成）；
    3. **删桶级联删钥**：同事务 bucket_delete + cred_delete 双 op（复制协议零变更）；前置校验空桶 + 无在途 multipart（收口 S-19）；
    4. **凭据接口收敛**：移除 `POST /creds` 与 `DELETE /creds/{ak}`；rotate 改挂桶路径 `POST /buckets/{name}/rotate`（无钥桶调用即自愈补发 AK+SK，兼容旧二进制建的桶）；`GET /creds` 并入 `GET /buckets`（桶列表带 access_key，无 secret）；"冻结租户"= rotate 到随机新值不外发（可逆）。
    - KEK 丢失恢复已核对：rotate 不需旧密文可解（ListCreds 不解密、新 KEK 重 seal、upsert），逐桶 rotate 即全量恢复；docs/02"health 自检报不可读条数"未实现，本轮补上（WebUI 桶列表标注）。
    - 不做嵌套桶/多密钥（对标厂商的"嵌套桶"实为前缀伪装的层级委托，与本修复方向相反；docs/01 不做 IAM/策略的边界不变）。不并入 buckets 单表（动已定稿复制协议，收益不值）。enabled 列保留不动（前向钩子，零成本）。

- [x] **S-02 oplog 无截断任务，元数据库无限增长**
  - 位置：`meta/oplog.go:85` TruncateOplog **无任何生产调用方**（仅测试引用）
  - 后果：每次写操作追加全量状态 JSON op，meta.db 随写入量线性膨胀（与 docs/03 设计的截断策略不符）；长期运行影响快照时长、同步内存占用，最终拖垮节点。
  - 建议：按 docs/03 实现后台截断：保留至 `min(所有已注册从节点 ack seq, 最新快照 seq) − 宽限期`；无从节点 ack 则不截断（该语义已写文档）。可挂进现有 GC 循环（gc.go）同频执行。
  - 验收：注册从节点并追平后，oplog 行数不随持续写入无限增长；无从节点时确认不截断。
  - **决议（2026-10-21）**：按建议实施，挂进 GC 循环同频执行；与 S-03 共用同一"有效从节点"定义（注册且 last_seen 在活跃窗口内），窗口内无人 ack 则不截断。

- [x] **S-03 GC 清扫门控可被僵尸 slave 注册永久阻塞，trash 无限膨胀**
  - 位置：`meta/runtime.go:33` MinSlaveAck 统计 `slaves` 表全部行；注册行**无过期机制**
  - 场景：一次 `POST /register` 后从未 ack 的 slave 行（last_acked=0）使 min 恒为 0 → `GateOpen` 永假 → trash 永不物理清扫。与 S-02 叠加：磁盘与元数据双膨胀。
  - 建议：门控改用 `last_seen_ns` 活跃窗口（如 7 天未见即视为离线、不计入门控），或提供 admin 端点删除僵尸 slave 行；注意与 docs/03 "无从节点 ack 则不截断"语义的边界（活跃窗口内无 ack 仍不截断，防落后从节点丢数据）。
  - 验收：注册一个不 ack 的 slave，超过窗口后清扫恢复；正常从节点不受影响。
  - **决议（2026-10-21）**：按建议实施；活跃窗口默认 7 天可配；截断（S-02）与清扫门控统一使用该"有效从节点"集合。

- [x] **S-04 长期凭证无强度下限（admin token / KEK / env repl token）**
  - 位置：`cmd/xmd/main.go:61-67`（仅查空）、`config/config.go:193`、`node.go:121`（env repl token <8 仅 WARN）
  - 后果：默认监听 0.0.0.0 的形态下，`XM_ADMIN_TOKEN=a` 即可启动；KEK 同理（低熵 KEK 直接削弱全部凭据密封）。运行时 repl token 有 ≥8 强制（SetReplToken），env 路径只警告——不一致。
  - 建议：三者统一最小长度（建议 admin/KEK ≥16、repl ≥8）拒启或至少醒目 WARN；KEK 额外提示"应为高熵随机串（低熵 KEK 无 KDF 加持）"。
  - 验收：短凭证启动被拒（或按选定的软/硬策略给出明确行为）。
  - **决议（2026-10-21）**：统一硬下限、拒启——admin token ≥16、KEK ≥16、repl token ≥8，env/YAML/运行时三条路径一致（运行时 repl 已是 ≥8，补齐其余）；docs/05 env 表标注并提示高熵随机串。

- [x] **S-05 明文 HTTP 下 WebDAV Basic 将 SK 明文上网**
  - 位置：`webdav/router.go:28`（Basic）；docs/01"必做清单"含"协议入口 TLS"，docs/05 又将 TLS 委托给反代——**文档内部不一致**，实现为无内置 TLS
  - 后果：S3 面验签不回传秘密、SFTP 自带 SSH 加密，唯独 WebDAV 在无 TLS 反代直连时 SK 可被动嗅探。属部署面风险，但当前文档两处口径打架。
  - 建议：①统一文档口径（推荐：明确 v1 不内置 TLS、必须经 TLS 反代/隧道暴露 :9000，并在 README/docker 说明置顶）；或②实现可选的监听面 TLS（cert/key 配置项，仅数据面与公共读面需要）。短期内至少完成①。
  - 验收：文档口径唯一；若实现②，自签/正式证书各跑一遍三协议冒烟。
  - **决议（2026-10-21）**：仅文档，不内置 TLS/自签证书（部分 web 服务器不支持回源自定义证书站点）。docs/01"协议入口 TLS"措辞修正为"传输安全由部署层提供"（定稿改动走 ADR），docs/05 安全基线强化：:9000/:9004 对外必须经 TLS 反代，WebDAV Basic 明文 SK 不可裸奔。

### P3（加固 / 边角 / 一致性）

- [x] **S-06 公共读面 500 响应携带内部错误文本（可含服务器绝对路径）**
  - 位置：`pubread/pubread.go:50/63/93/113`（`http.Error(w, err.Error(), 500)`）；错误源如 `blob/blob.go:155` 用 `%q` 带完整路径
  - 后果：未鉴权端口上，触发 blob 打开失败（如条目指向损坏/被动的 blob）即向匿名者泄露 `D:\...\blobs\...` 路径布局。S3 面 `writeXMLError(..., err.Error(), ...)` 同病但需凭据，级别更低。
  - 建议：500 一律回固定文案，详情进 slog（带 reqID 便于排障）。
  - 验收：人为制造 blob 缺失后，:9004 匿名请求 500 响应体无路径、无底层错误串。

- [x] **S-07 公共读面缺 `X-Content-Type-Options: nosniff`**
  - 位置：`pubread/pubread.go`（响应头组装处）
  - 后果：公共桶对象 Content-Type 由上传者控制，配合浏览器 MIME 嗅探存在被动的内容注入面（HTML/SVG 在反代域名下执行）。
  - 建议：公共读面所有 2xx 响应加 `X-Content-Type-Options: nosniff`（与"不发缓存头"立场一致：只做无副作用加固，策略归反代）。文档同时提示"公共桶 = 放弃该桶访问控制（含内容执行面）"已有，保留。
  - 验收：e2e 断言响应头存在。

- [x] **S-08 非区间 GET 先发 200 再打开数据流，失败时响应已无法回滚**
  - 位置：`s3/handler.go:352-365`（WriteHeader(200) 后才 store.Get）、`pubread/pubread.go:105-115` 同型；两个 Range 分支已是正确顺序（先 Get 后 WriteHeader）
  - 后果：流打开失败时对客户端表现为"200 + 截断体"，仅靠 Content-Length 不符被发现；语义应尽量 5xx。
  - 建议：统一为先 Get 后 WriteHeader（Range 分支已有实现可照搬）。
  - 验收：单测构造 Get 失败路径断言 5xx。

- [x] **S-09 aws-chunked 帧行长无上限（持凭据者内存 DoS）**
  - 位置：`s3/auth.go:324`（`c.r.ReadString('\n')` 无界累积）
  - 后果：合法凭据客户端发送超长无换行块头可撑爆内存。需要凭据才可触发，且配额/SK 轮换可兜底，故仅 P3。
  - 建议：块头行限长（如 8KB）超限报 ErrInvalidArgument。
  - 验收：单测超长帧头被拒。

- [x] **S-10 S3 recover 将 panic 内容回显客户端**
  - 位置：`s3/handler.go:50-53`（`fmt.Sprint(rec)` 进 XML Message）
  - 建议：panic 详情仅入日志，响应体固定 InternalError 文案。
  - 验收：构造 panic 路径断言响应无堆栈/内部值。

- [x] **S-11 SSH 主机密钥任何读取错误都静默重生成并覆盖**
  - 位置：`sftp/server.go:101-117`（`os.ReadFile` 任意 err → 生成新键覆盖写）
  - 后果：权限/损坏等非"不存在"场景下主机键被换，客户端遭遇 host key change 告警（TOFU 信任链被动摇）；也掩盖磁盘问题。
  - 建议：仅 `os.IsNotExist` 时生成；其他读取错误直接启动失败；已存在文件拒绝覆盖写。
  - 验收：chmod 000 后启动失败并报因。

- [x] **S-12 meta.db 文件权限为 umask 默认（通常 0644），密封凭据密文本地可读**
  - 位置：SQLite 由 modernc 驱动默认权限创建；数据目录 `MkdirAll 0755`（store.go:84）
  - 后果：同机非 root 用户可读 creds 密文与全部元数据（node-state.json 已是 0600，meta.db 不是）。单服务部署下影响有限，属纵深加固。
  - 建议：打开库后 `os.Chmod(meta.db, 0600)`（含 -wal/-shm）；或进程级 UMask。docs/05 安全基线补一句"数据目录属主即服务账户"。
  - 验收：Linux 容器内 `stat -c %a meta.db` = 600。

- [x] **S-13 从节点 HTTP client 无超时，同步循环可被挂死连接卡住**
  - 位置：`repl/slave.go:64`（`&http.Client{}`）
  - 建议：加合理 Timeout（blob 下载大文件需宽松，可用 per-request timeout 区分控制类与传输类请求）。
  - 验收：模拟主端 accept 后不响应，同步循环按超时退避重试而非永久阻塞。

- [x] **S-14 ReplaceMeta 存在"先删后改名"窗口，且快照无预校验/无校验和**
  - 位置：`store/store.go:299-318`（Remove meta.db → Rename）；`repl/slave.go:126-156`（Bootstrap 直接信任下载体）
  - 后果：窗口期崩溃 = 元数据文件丢失（快照临时文件仍在，但需人工恢复）；传输损坏的快照会在 Rename 后打开失败才暴露。
  - 建议：先 `meta.Open` 校验下载文件可开可查，再把旧 meta.db 改名为 `.bak`（而非删除），最后原子改名接管；主端 `/snapshot` 可顺带返回 sha256 头供校验。
  - 验收：注入截断的快照文件，Bootstrap 拒绝且本地元数据完好。

- [x] **S-15 admin 普通接口鉴权失败无延迟（仅签发端点有 250ms）**
  - 位置：`api/auth.go:86-102`（auth 中间件无延迟；`adminAuth` 有）
  - 后果：持有任意 admin 端点可达性的攻击者可全速爆破 X-Xm-Token。docs/06 #13 只记录了签发面，此为同类面更宽。
  - 建议：auth 中间件失败路径同样加固定小延迟（或复用 adminAuth 策略）。
  - 验收：错 token 请求耗时 ≥ 设定延迟。

- [x] **S-16 认证无速率限制 + 用户自设 SK 仅 ≥8 字符**
  - 位置：`store/creds.go:56`（len(secret) ≥ 8）；SFTP MaxAuthTries=3 但重连无限（sftp/server.go:37）
  - 后果：弱 SK + SFTP 密码爆破面 = 逐凭据慢速猜解（服务端生成的 48 字符 SK 无此问题）。
  - 建议（按代价递增任选）：①admin 创建凭据时对自备 secret 提高下限（如 ≥24）或强烈警告；②SFTP/数据面加简单的每源连接/认证频率限制；③文档明示"自备 secret 需高熵"。
  - 验收：按所选项补测试或文档。

- [x] **S-17 WebDAV 配额预检传错 key（含桶名前缀），覆盖写抵扣失效**
  - 位置：`webdav/router.go:39`（`trimSlash(rest)` 是 `bucket/key` 而非 key）
  - 后果：配额临界时覆盖写被预检误拒 507（FS 层真正的写入限流用的是正确 key，纯功能性误拒，非越权）。
  - 建议：用 `cutPath` 的 tail 或复用 FS 的 normPath 语义。
  - 验收：近配额覆盖写单测通过。

- [x] **S-18 `max-keys=0` 被当默认 10000（S3 语义偏离）**
  - 位置：`s3/handler.go:132-135` + `store/objects.go:383`（max≤0 → 10000）
  - 后果：客户端显式要 0 条（探测性列举）却收到至多 1 万条。与安全无直接关系，顺手修。
  - 建议：0 合法直通（返回空列表 + IsTruncated），负数才回默认。
  - 验收：max-keys=0 返回空列表。

- [x] **S-19 DeleteBucket 不检查在途 multipart 会话**
  - 位置：`store/store.go:184-198`（仅查 objects>0）
  - 后果：空桶但存在在途上传时可删桶，留下孤儿 uploads 行与 pending 计数（GC 超时清理时 AdjustUsage 落空）。数据无损，账目留尾巴。
  - 建议：删除前同时校验无进行中会话（与 S-01 一并处理最顺）。
  - 验收：有在途会话的桶删除被拒。

- [x] **S-20 admin 破坏性操作无审计留痕**
  - 位置：`api/admin.go`（cred 创建/轮换/删除、桶删除、promote 有 slog 但凭据族没有；均未记来源 IP）
  - 后果：凭据被谁何时轮换无法事后追溯——基础设施定位下审计是硬需求。
  - 建议：admin 面统一加一行结构化审计日志（方法、路径、来源 IP、结果），凭据族操作必须含 AK（不含 SK）。

### 设计确认项（记录取舍，不算缺陷，无需修复）

- **X-Amz-Content-Sha256 不对实体校验、STREAMING chunk 签名忽略**（s3/auth.go:72-75、299 注释）：SigV4 的传输中防篡改未提供；存储完整性由服务端入库哈希兜底（落盘即 sha256，伪造体也会被如实存储并哈希）。攻击者需持有效凭据才有意义。**与 MinIO 等实现同取舍，可接受**；若未来面向不可信代理链路可补载荷校验开关。
- **region 不固定**：验签接受客户端声明的任意 region（HMAC 覆盖），兼容性取舍。
- **InvalidAccessKeyId / SignatureDoesNotMatch 细分**：泄露 AK 有效性——与 AWS 原生行为一致。
- **会话 token 不绑源 IP、不可续期**：双 token 定位即如此（99-D023⑤）。
- **`/health`、`/metrics` 在鉴权后**：docker HEALTHCHECK 自带 token，已知设计。
- **快照/bootstrap 通道信任 repl token**：复制面凭证即信任边界（配合部署层 TLS 建议）。

### 部署面建议（写给使用者，不改代码）

1. :9000（S3+WebDAV）必须经 TLS 反代或隧道暴露公网（WebDAV Basic 明文 SK，见 S-05）；反代透传 Host、不改路径、关缓冲（docs/05 已写）。
2. :9002/:9003 不进公网（docs/05 基线）；远程管理走 SSH 隧道。
3. 对外开放 :9004 前确认桶公共开关的授予流程（公共桶 = 放弃访问控制）；反代层自行加缓存策略与限流。
4. 桶尽量设配额（quota=nil 桶可被持凭据者写满磁盘——单对象有 5GB/1TB 上限但无总量上限）。
5. KEK/admin token/repl token 均为长高熵随机串（≥32 字符随机）；轮换路径见 docs/05。
